## 개요

애플리케이션을 컨테이너로 실행하면 배포 환경을 표준화하기 쉬움. 하지만 컨테이너가 수십 개, 수백 개로 늘어나면 어디에 배치할지, 장애가 나면 어떻게 복구할지, 트래픽이 늘면 얼마나 확장할지 같은 운영 문제가 생김.

쿠버네티스(Kubernetes, K8s)는 이런 문제를 자동화하기 위한 오픈소스 플랫폼임. 컨테이너의 배포, 확장, 복구, 네트워크 연결, 설정 관리를 선언적으로 처리해 대규모 서비스 운영을 도움.

---

## 쿠버네티스란?

쿠버네티스는 컨테이너 오케스트레이션 도구임. 오케스트레이션은 여러 컨테이너를 원하는 상태로 유지하기 위해 생성, 배치, 재시작, 확장, 삭제를 자동으로 조율하는 일을 말함.

쿠버네티스는 구글이 내부에서 사용하던 대규모 클러스터 관리 경험을 바탕으로 공개한 프로젝트이며, 현재는 CNCF(Cloud Native Computing Foundation)에서 관리하는 클라우드 네이티브 생태계의 핵심 기술로 자리 잡음.

---

## 쿠버네티스를 사용하는 이유

### 자가 치유

컨테이너나 파드가 비정상 종료되면 쿠버네티스는 이를 감지해 다시 시작하거나 새 파드로 교체함. 운영자가 직접 서버에 접속해 프로세스를 확인하지 않아도 설정한 상태를 유지하려고 동작함.

### 자동 확장

트래픽이나 리소스 사용량이 증가하면 파드 수를 늘려 부하를 분산할 수 있음. HPA(Horizontal Pod Autoscaler)는 CPU, 메모리, 사용자 정의 지표 등을 기준으로 파드를 자동 확장하고, 필요에 따라 클러스터 노드 확장도 함께 구성할 수 있음.

### 로드 밸런싱

쿠버네티스의 Service는 여러 파드 앞에 고정된 접근 지점을 제공하고 요청을 분산함. 파드가 새로 생성되거나 삭제되어 IP가 바뀌어도 서비스 접근 방식은 유지됨.

### 무중단 배포와 롤백

Deployment를 사용하면 새 버전을 순차적으로 배포하는 Rolling Update를 적용할 수 있음. 배포 중 문제가 생기면 이전 버전으로 되돌릴 수 있어 서비스 중단 위험을 줄일 수 있음.

---

## 핵심 구성 요소

### 클러스터

클러스터는 쿠버네티스가 관리하는 전체 실행 환경임. 여러 노드로 구성되며, 크게 컨트롤 플레인과 워커 노드로 나뉨.

### 컨트롤 플레인

컨트롤 플레인은 클러스터의 상태를 관리하는 중심부임. API 서버를 통해 명령을 받고, 스케줄러가 파드를 어느 노드에 배치할지 결정하며, 컨트롤러가 실제 상태를 원하는 상태와 맞춤. 클러스터 설정과 상태 정보는 etcd에 저장됨.

### 워커 노드

워커 노드는 실제 애플리케이션 컨테이너가 실행되는 서버임. 각 노드에는 kubelet이 실행되어 컨트롤 플레인의 지시를 받고, 컨테이너 런타임이 컨테이너를 실행함. kube-proxy는 네트워크 연결과 트래픽 전달을 담당함.

### 파드

파드(Pod)는 쿠버네티스에서 배포되는 가장 작은 단위임. 보통 하나의 애플리케이션 컨테이너를 담지만, 필요하면 긴밀하게 연결된 여러 컨테이너를 함께 실행할 수도 있음. 같은 파드 안의 컨테이너는 네트워크와 스토리지를 공유함.

### 디플로이먼트

디플로이먼트(Deployment)는 파드를 어떤 이미지로 몇 개 유지할지 정의함. 예를 들어 파드 3개를 유지하도록 설정하면 하나가 죽어도 쿠버네티스가 새 파드를 만들어 개수를 맞춤.

### 서비스

서비스(Service)는 파드에 안정적인 접근 주소를 제공함. 파드는 재시작될 때 IP가 바뀔 수 있으므로, 서비스가 고정된 진입점 역할을 함.

---

## 도커와 쿠버네티스의 차이

도커(Docker)는 컨테이너 이미지를 만들고 실행하는 도구에 가까움. 개발자는 도커를 사용해 애플리케이션과 실행 환경을 하나의 이미지로 패키징하고 로컬 또는 서버에서 컨테이너를 실행할 수 있음.

쿠버네티스는 이렇게 만들어진 컨테이너를 여러 서버에 배치하고 운영하는 도구임. 컨테이너를 몇 개 실행할지, 어느 노드에 둘지, 장애가 나면 어떻게 복구할지, 외부 트래픽을 어떻게 연결할지 관리함.

정리하면 도커는 컨테이너를 만들고 실행하는 데 초점이 있고, 쿠버네티스는 여러 컨테이너를 안정적으로 운영하는 데 초점이 있음.

---

## 도입 전 체크할 점

### 인프라 환경

쿠버네티스는 온프레미스, 퍼블릭 클라우드, 하이브리드 환경에서 모두 사용할 수 있음. 직접 클러스터를 구축할 수도 있고, EKS, GKE, AKS 같은 관리형 쿠버네티스 서비스를 사용할 수도 있음. 운영 부담을 줄이고 싶다면 관리형 서비스를 우선 검토하는 것이 좋음.

### 학습 곡선

쿠버네티스는 강력하지만 익혀야 할 개념이 많음. YAML 매니페스트, 네트워크, 스토리지, 리소스 제한, 권한 관리, 배포 전략 등을 이해해야 안정적으로 운영할 수 있음.

### 비용과 운영 효율

쿠버네티스 자체는 오픈소스지만 클러스터 운영에는 인프라 비용과 운영 인력이 필요함. 작은 서비스에서는 오히려 복잡도가 커질 수 있고, 서비스 규모가 커질수록 자동화와 표준화의 효과가 커짐.

---

## 클라우드 네이티브 생태계와 쿠버네티스

쿠버네티스는 단순히 컨테이너를 실행하는 도구를 넘어 클라우드 네이티브 플랫폼의 기반이 되었음. Prometheus, Argo CD, Istio, Helm, Kubeflow 같은 많은 도구가 쿠버네티스 위에서 동작하거나 쿠버네티스와 함께 사용됨.

특정 클라우드에 종속되지 않고 비슷한 방식으로 애플리케이션을 배포할 수 있다는 점도 장점임. 멀티 클라우드, 하이브리드 클라우드, 대규모 마이크로서비스 운영에서 쿠버네티스가 자주 선택되는 이유임.

---

## 요약

쿠버네티스는 컨테이너를 대규모로 운영하기 위한 오케스트레이션 플랫폼임. 파드, 디플로이먼트, 서비스, 컨트롤 플레인, 워커 노드 같은 구성 요소를 통해 애플리케이션을 원하는 상태로 유지함.

도커가 컨테이너를 만들고 실행하는 도구라면, 쿠버네티스는 그 컨테이너들을 여러 서버에서 안정적으로 운영하는 도구임. 서비스 규모가 커지고 배포 자동화, 장애 복구, 확장성이 중요해질수록 쿠버네티스의 가치가 커짐.
